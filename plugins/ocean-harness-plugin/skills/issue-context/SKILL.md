# Issue 工作空间上下文契约

定义 issue 运行工作空间中两个 AI 上下文文件的结构与更新规则。生成方（`/ocean-harness:issue-refine`）必须遵守本契约；消费方（`/ocean-harness:issue-dev`）只读引用，执行期不修改两文件。

**状态与上下文分离**：子任务清单、状态、进度以数据库为唯一真相源（CLI `issue_child_list` / tracker 看板），上下文文件不记录任何状态——同一数据只留一份，杜绝双写漂移。CLAUDE.md 只是需求上下文的本地快照。

## 文件位置

两个文件均位于工作空间根目录（即终端 cwd，`{workspace_base_dir}/{issueId}/`）：

```
{baseDir}/{issueId}/
├── AGENT.md      # 静态上下文：项目信息、编码规范、架构概览（首次生成，仅增量补充）
├── CLAUDE.md     # 需求上下文快照：原始需求存档、润色后需求、注意事项（首次生成，增量重跑可修订）
└── repo/{name}/  # 关联仓库（agent_{issueId} 分支）
```

## CLAUDE.md 模板（需求上下文快照）

首次生成时严格按以下结构写入；增量重跑按下方「增量重跑规则」修订：

```markdown
# {issue name}

> 本文件由 /ocean-harness:issue-refine 生成，是需求上下文的本地快照。
> 子任务清单与进度以数据库为准（tracker 看板 / CLI issue_child_list），本文件不记录状态。

## 任务信息

- Issue ID: {issueId}
- 关联仓库: {repo1}（基准分支 {branch1}）、{repo2}（基准分支 {branch2}）

## 原始需求（存档）

{用户原始描述原文，一字不改，仅供追溯——issue-refine 会用润色稿覆盖 issue 描述，原文唯一留档于此}

## 润色后需求（快照）

> 与 issue 描述同步生成；issue 描述为权威版本，后续在 tracker 中的修改不回填本文件。

### 背景

{为什么要做这件事，业务/技术背景}

### 目标

{完成后达到什么效果，一两句话}

### 需求明细

{分点列出澄清后的具体需求，每点可独立验证}

### 边界与非目标

{明确不做什么，防止范围蔓延}

### 验收标准

{可验证的完成判据清单}

## 注意事项 / 约束

- {澄清过程中确认的约束、技术决策、风险点}
```

**模板硬性约束**：

- **不写入子任务清单、状态、进度等任何随执行变化的数据**——issue-dev 从 DB（CLI `issue_child_list`）获取清单与状态，凭 CLI 返回的子任务 id 回写，不经本文件
- 「原始需求（存档）」段一经写入永不修改

## 增量重跑规则（issue-refine 执行）

issue-refine 增量模式修订 CLAUDE.md 时：

- **「原始需求（存档）」段永不修改**
- 可修订：润色后需求各小节、「注意事项 / 约束」段、「任务信息」的标题与关联仓库（如有关联变更）
- 子任务的增删不经本文件：新增走 `issue_child_create`，作废走 `issue_child_update` 置 CANCELLED（须先经用户确认）；已有子任务的 DB 状态一律不动

## AGENT.md 模板（静态上下文）

首次生成时按以下结构写入；已存在时只允许**追加或修订对应小节**，不得整体重写：

```markdown
# {项目名} — 项目上下文

> 由 /ocean-harness:issue-refine 首次生成（静态上下文，仅增量补充，不随任务重写）。

## 项目概述

{一段话：项目定位、技术栈、主要能力}

## 关联仓库

| 仓库 | 目录 | 基准分支 | 说明 |
|------|------|----------|------|
| {name} | repo/{name} | {branch} | {仓库职责} |

## 架构概览

{分层结构、核心模块、数据流；从源码分析得出}

## 编码规范（AI 从代码库推断）

{命名约定、分层规则、i18n/注释惯例、明确禁项}

## 关键目录

{目录树 + 每个关键目录一句话说明}
```

## 子任务拆分规范（issue-refine 执行）

- **可验证**：每个子任务必须有明确完成标准（写入子任务的 description），杜绝「优化一下」「完善功能」类表述
- **粒度适中**：一个子任务 = 一次可独立验证的交付；避免过细（纯机械步骤）与过粗（跨多模块大改）
- **按执行顺序排列**：有依赖关系的任务，被依赖者排前
- **数量建议 3~8 项**：小需求不硬拆（无子任务时 issue-dev 整体执行 issue）
- **状态默认 `BACKLOG`**：创建后由 issue-refine 按双条件流转父 issue 为 `TODO`（父当前为 BACKLOG 且不存在 IN_PROGRESS/DONE 子任务；不满足则不流转并在摘要说明原因——父状态变化会无差别级联子任务，可能打回已有进度）
